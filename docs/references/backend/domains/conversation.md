# conversation —— 对话线程容器

## 1. 定位 + 心智模型

线程**容器**实体：身份（title/pin/archive/软删）+ 线程级配置（systemPrompt / attachedDocuments / modelOverride / **workDir（驻地）**——用户可改，chat 运行时消费）。**消息不在这**（归 messages/chat）。系统写字段在记录里但**不进 PATCH 面**：`Summary`/`SummaryCoversUpToSeq`（压缩器写）、`AutoTitled`（chat 首回合自动命名后写、绝不覆盖用户标题）、`Unread`（持久布尔列：完成的 assistant 回复未看=true，随 TouchLastMessage 折进同一 UPDATE 原子设、`MarkSeen` 清——见下 hasUnread）。

**PATCH 三态**：`ModelOverride **ModelRef`——nil=不变、&nil=清除、&(&ref)=设置（指针的指针表达三态）。**写时校验**（F153，经 `modelref.Validate`，与 agent override / workspace scenario default 同源）：设置时校结构 + **apiKeyId 存在性**（引用不存在 key 即 `API_KEY_NOT_FOUND`、非只 chat 时失败）；清除（&nil）跳过；modelId 拼写不校、留 fail-loud-at-chat（无权威 model 目录）。List：**Archive 三态枚举** `ArchiveScope`（非重载 *bool）——`ArchiveActive`（零值/默认，仅活跃）/`ArchiveArchived`（仅归档）/`ArchiveAll`（活跃+归档同列，rail「显示已归档」用，归档行带 `archived=true` 供灰点）。HTTP `?archived=`：缺省/其余=active、`true`/`1`/`archived`=archived-only、`all`=all。store 按 scope 套恰好一个 archived 谓词（ArchiveAll 不加）。`list_conversations` 工具 `includeArchived:true` → ArchiveAll（旧 *bool 设计下它误以为 nil=all、实际 store nil=active-only 静默漏归档，三态枚举修此）。**Sort 可选**——`activity`（默认，置顶优先再 `last_message_at` 降序，最近聊过）、`created`（置顶优先再 `created_at` 降序）或 `name`（置顶优先再 `title` A–Z，**大小写不敏感** `COLLATE NOCASE`，id 升序为同名 tiebreaker）。activity/created 经 orm `Page`（时间键、降序）；name 经 `PageAsc`（字符串键、升序、NOCASE）——store 据 Sort 切 `Order(... <key> ...)` + `PageKeyset(<key>)`，游标键随排序列对齐（见 [orm.md](../foundation/orm.md)）；name 另有覆盖索引 `idx_conversations_ws_title`（与 ORDER BY/keyset 同 `COLLATE NOCASE`）。故**切换 Sort 须丢弃游标**（一种排序下的游标在另一种下无意义）。未知/空 Sort → activity（不报 400）。**Search 可选**——`?search=<term>` 对 `title` 大小写不敏感子串过滤（orm `WhereLike`：转义 `%`/`_` 通配符、空 term 不过滤），作额外 WHERE 谓词与 archive 并列、**不改排序键**，故换 search 同样须从头翻（丢弃游标）。

**native model options**：与 workspace default / agent override 同源的 `modelref.Validate` 在写时除结构和 key 存在性外，还校验非空 `options` 是否精确属于该已探测 key/model 公开的 native knob 及其值。未知字段→422 `MODEL_OPTION_UNSUPPORTED`，非法值→400 `MODEL_OPTION_VALUE_INVALID`；空 options 的 modelId 则仍不做硬目录校验，保留 custom/未探测模型 invoke 时 fail-loud 的路径。

**last_message_at**（最近活跃排序键）：普通列（非 `,updated` tag，故 pin/改名/换模型不重排）。创建时种为 now，chat 经 `ConversationReader.TouchLastMessage` 在每个用户回合刷新——"最近聊过"上浮，ChatGPT 式 Today/Yesterday 分组的依据。

**isGenerating**（派生只读，`db:"-"`）：List/Get 据 chat 注入的 `GeneratingQuerier` 端口逐行填——该对话当前是否有在途 assistant 回合。让刚连上 / SSE 重连的客户端冷启动活动圆点（无需等下一帧）；纯运行时状态、不落库、不进 PATCH。与 canceler 同款后注入端口破 chat↔conversation 环。

**awaitingInput**（派生只读，`db:"-"`）：List/Get 据 chat 注入的 `AwaitingInputQuerier` 端口逐行填——该对话当前是否有 ≥1 个待决人在环 interaction（等用户批准/回答、回合才续）。镜像 isGenerating（同款后注入端口破环），使 rail 显「等你」点。待决 interaction 只活在**内存 humanloop broker**（无 DB 表、刻意 ephemeral——重启即无、events.md），故恒派生、不落库、不进 PATCH；冷启动经 List/Get、`GET /{id}/interactions` 精确重同步,实时经 messages 流的 `interaction` 信号（create + resolve 两态 ephemeral——resolve 帧带 `resolved:true` 使前端清「等你」点而不靠 tool_result 反推）。

**hasUnread**（持久只读，列 `unread`，**非** `db:"-"`）：有一条**完成的** assistant 回复用户尚未看 → true，即「你不在时答完了」的 rail 绿点。**用存布尔、非时间/seq watermark**——单用户、会话级二元量不需读位置粒度，直接存答案绕开墙上时钟比较（无 NTP 回拨 / 粗 tick 误判），重启照样在（是列）。`TouchLastMessage` 把它折进同一条原子 UPDATE：用户发送 `unread=false`（发即是看，自己的消息绝不未读）、assistant **完成**终态 `unread=true`（取消/出错终态不算）；`MarkSeen`（`:seen` 动作，用户打开线程没发消息时）清 false。系统写、线缆只读、不进 PATCH（同 AutoTitled）。实时翻转靠**既有 messages 流**的 `message_stop`（不新增 SSE，守 E1）：连着的客户端收到非聚焦线程的 finalize 帧即本地置未读，打开它时 POST `:seen` 清。

**forkedFromConversationId / forkedFromMessageId**（持久只读两列）：分叉血缘——源线程 + 前缀复制停在的那条消息（含它）。fork 时一次写定、永不更新：分叉**是**新线程、不是旧线程的视图，故这对 id 是**溯源、非活链接**——源日后可被删，届时 id 悬空、UI 只是不显血缘行（无需级联、无需外键）。两者皆空 = 普通线程。系统写、线缆只读、不进 PATCH（同 Summary / AutoTitled）。

**workDir（驻地，WRK-077 WD1）**：对话**可选**的工作目录。用户原话定调——「这个工作目录我是希望是一个可选项，如果选了的话只是告诉 AI，我们 zoom in 到这里。但是如果想看外面什么的，都可以」——故它是**zoom、不是牢笼**，全部语义就三件事 + 一道闸：

1. **相对路径以它为根解析**：`pkg/fspath` 是路径规则的唯一物理执行点，六个吃路径的工具（`Read`/`Write`/`Edit` + `LS`/`Glob`/`Grep`）全改走 `ExpandIn(root, p)`——未挂时它**逐字等于**旧的 `Expand`（相对即拒，`FSPATH_NOT_ABSOLUTE`），挂了则把仍相对的路径接到根上、**绝对路径原样放行**（含指向根外的）。搜索三件套一并改是刻意的：让 `Read("src/x.go")` 成立而 `Grep(path:"src")` 不成立，是同一条规则的两种答案。
2. **`Bash` 的 `cmd.Dir` 设为它**（此前**不设** `Dir`、子进程继承后端目录，那条旧立法已在 `tool/shell/shell.go` 包注释重述为当前事实）。已挂但**不可用**的目录（用户挂完之后移走/删了）**予以拒绝**、不静默回落——回落会让命令在 sidecar 自己的目录里跑、而线程仍声称住在别处，于是命令里每个相对路径都悄悄打到错误的树上。
3. **每轮 system prompt 带一段 `work_dir`**（路径 + 分支，见 [chat.md](chat.md) §3.6）。
4. **越界写强制人闸**：`Write`/`Edit` 的目标 canonical 路径落在子树**外** → **无视 LLM 自报的 danger 等级**、强制走**既有**人闸（`loop.dispatchWithGate` + `app/humanloop`，**零改动可用**）。**读永不设闸**。判定见 [foundation/loop.md](../foundation/loop.md) 的人闸两触发条与 [foundation/platform-pkgs.md](../foundation/platform-pkgs.md) 的 `fspath.Inside`。

**PATCH 面是朴素指针、非三态**：该列的空值已表示「未挂」，故 `""` **就是**清除、没有第三种状态要表达（`modelOverride` 之所以要指针的指针，只因它清除后的值是 nil 结构指针而不是 `""`）。写时经 `fspath.Expand` **归一化**（展开 `~`、`Clean`），故落库与回显恒是真绝对路径、每个下游读者不必再猜一遍；**唯一校验是物理的**——非绝对即 422 `CONVERSATION_INVALID_WORK_DIR`（一个扎不住任何东西的根，会让此后每次工具调用静默失效），而**存在性刻意不校验**（目录被移走/删掉是合法且可渲染的状态，在写时强求它等于为一个下一秒就可能改变的条件拒掉一次诚实的挂载）。切换时发 `conversation.work_dir` 动作（与 rename/pin 同径）。

**中途切换落一条 `marker` 块**：驻地在线程中途变了，往回翻的读者必须看见它变在**哪里**——`{kind:'workdir', from, to}`，经 chat 的 `MarkWorkDirMarker` 端口写（消息归 chat，故 conversation 用与 canceler/querier 同款后注入端口去找它；写失败只是不留标记、**绝不**阻塞用户的切换）。**空线程不落标记**（没有「之前」，而首发前挂驻地恰是常见路径）；**重复 PATCH 同一路径不落标记**（一个把整个头回显回来的客户端不该在线程上盖章）。块型立法见 [database.md](../database.md) 的 `marker` 专条。

**驻地分组（WRK-077 WD1.5）——rail 左岛按驻地分组的后端半边**。前端的四段结构是「新对话·搜索 / 置顶 / 📁 驻地组 ×N / 最近（仅无驻地）」，而**后端在此存在的唯一理由是防「分组撒谎」**：rail 是无限翻页的，若在一窗内做客户端分组，组成员与计数会随滚动**漂移**——组头会报出一个在 workspace 什么都没变时自己会变的数。三件小件，全部围绕这一点：

1. **`GET /conversations/workdir-groups`**（投影，`Repository.WorkDirGroups`）→ `[{workDir, activeCount, archivedCount, lastMessageAt}]`，对整个 workspace **一次 GROUP BY**（走新索引 `idx_conversations_ws_workdir`，见 [database.md](../database.md)），按 `MAX(last_message_at) DESC, work_dir ASC` 排（全序，故两次相同请求绝不互换）。**组是投影、不是实体**——不建表、无 id、无生命周期：一个组存在的时长恰好等于「还有未置顶对话带着那个 `work_dir`」，最后一个离开它就自行消失，故**不做「空目录组」管理**。**被计数的集合是「未置顶」**：置顶对话被提到 rail 自己的置顶段、必须**恰好出现一次**，故在此计入它会让组头的数与它下面的行不一致。**未挂线程不构成组**（`work_dir = ''` 不出现——它们没有文件夹头、没有 ⋯ 菜单）；软删的行不算。`activeCount`/`archivedCount` **分列**（一趟 `COUNT … FILTER`）使 rail 的「显示已归档」开关自行取其一或求和、批量动作盘点二者之和，**而端点保持零参数**（N4 有界投影的「零参数」形，见 api.md 前言②）；`lastMessageAt` **跨两种归档态**，故切换视图绝不重排组序。
2. **List 两个新过滤**：`?workDir=`（**三态、按键是否出现读**：缺席=不过滤、**出现且为空**=仅未挂、有值=仅该驻地。domain 侧是 `ListFilter.WorkDir *string`——**朴素指针**，因为 `""` 在此是一个**有意义的过滤值**、不是「没有过滤」）· `?pinned=`（`PinScope` 三态：`PinAny` 零值=两者、`PinPinned`=仅置顶、`PinUnpinned`=仅未置顶）。**`?pinned=` 为何必要**：分组后 rail 的每条线程必须恰好出现一次，而「所有置顶线程」在其余各轴都按驻地过滤之后**再也**不能靠「置顶都落首页」的假定复原——住在一个**收起**的组里的置顶线程根本不会被取回来。于是置顶段拿到它自己的精确查询、驻地各轴要那个未置顶的补集，rail 端**零客户端重分桶**。
3. **两个集合级批量动作**（N5）：**`POST /conversations:archive-workdir`** / **`POST /conversations:delete-workdir`**，body `{workDir}`，返 `{workDir, archived|deleted}` = **真正改变**了几条。范围 = 该驻地下的**未置顶**对话（与组头计数逐字相同，故确认框盘点诚实；**置顶存活**——置顶是用户在说「这条我在意」）。archive 只动 `archived = 0` 的行（重跑答 0、不发回声）；delete **跨归档态**（破坏性动作不该静默取决于哪个视图开关开着）。**事务性**：`Repository.ArchiveWorkDir` / `SoftDeleteWorkDir` 在**一个**事务里 Pluck 出 id 集、施加**一条**语句、并**交叉核对**行数与 id 数——故一次静默的半个动作（某行被 BEFORE 触发器跳过、或未来两个 WHERE 漂移）会变成一次**回滚的错误**，而不是留下半个归档了的目录。**逐行级联在提交之后**跑、best-effort，与单条 Delete 同一套（停生成 + 丢 humanloop 授权 + relation 边 + 触点台账）；停生成因此落在写**之后**（单条 Delete 先停）——不读就无从知道 id 集，而在写之外读会让集合在读与写之间漂移，那个毫秒窗口里回合正流进一条没有读者到得了的行。**D1**：delete 只在**对话行**上盖 `deleted_at`，**绝不碰任何消息行**（`messages`/`message_blocks` 无 `deleted_at`、绝不物理删）；**文件系统分毫不动**——驻地只是行上一个字符串、此处当分组键读，故 UI 的用词永远是「删除全部对话」而**绝不是**「删除目录」。**不引入新错误码**：空 `workDir` → `400 INVALID_REQUEST`（`''` 是正当的列表过滤、但不是一个组；接受它会让一个请求扫掉每一条从未选过目录的线程）· 非绝对 → `422 CONVERSATION_INVALID_WORK_DIR`（WD1 的规则）。

**「消息行仍在」这条断言的落点**（诚实边界）：它**在 testend 黑盒里不可观测**——每条消息读路径都被一次对话存在性检查所辖，故一条已立碑线程的 `GET /{id}/messages` 按设计答 `404 CONVERSATION_NOT_FOUND`，线缆分不清「线程的行被立碑了」与「它的消息被抹了」。故 D1 的证明做在两张表都看得见的地方：后端单测 `TestDeleteWorkDir_NeverTouchesAMessageRow`（同库立起 messages schema、写一个真回合、删掉整组、再从 messages store 把 message 与 block 行直接读回来）。testend 断言线缆**能**证明的部分（立碑 404 而非 200-空、存活兄弟的逐字记录完好、组自行消失、**计数跨翻页不漂移**）。

**派生投影 `GET /{id}/workdir`**：`{path, exists, isGitRepo, branch?, dirty}`，**逐请求现算、零缓存**——文件系统与 git **就是**真相，缓存进对话行的生命周期会在用户于自己终端里切一次分支的那一刻成为谎。未挂对话返 **200 + 零投影**（不是 404——「这条线程没有驻地」是一个成功的回答，且驻地按钮也得渲染那一态）。WD1 的 git 段**只读**；`branches[]`（WD2）/ `worktrees[]`（WD3）本批不做。

**Fork（`POST /{id}:fork`）**（**`work_dir` 已随 WD1 加入复制集**——驻地正是被复制的那段对话「在谈的地方」，且分叉继承的前缀里满是在那个目录里跑过的工具调用，一个落在虚空里的分叉会让它自己历史中的每个相对路径都读不懂；它也正是让分叉与源落进同一个 rail 组的东西［WD1.5］）：分支模型是 **fork 成新对话**、**不是**树内分支——`messages`/`message_blocks` 是 D1 Log 表（append-only、无 `deleted_at`），树内分支要动 `seq`、三读形态、SSE 契约与前端 reducer 的根基，故否决；前缀复制是**纯追加**、对源零改写。**两半分工**：`Service.Fork(ForkInput)` 只写**头行**（源的 `system_prompt`/`attached_documents`/`model_override`/**`work_dir`** 逐字复制 + 血缘两列 + 调用方**已做好**的摘要携带决定 + 标题加 ` (fork)` 而 `auto_titled` 保持 false［那是可改的起步名、不是自动命名；源无标题则分叉亦无标题，使 chat 的自动命名仍有它的回合］；`archived`/`pinned` **刻意不复制**——分叉是你刚打开的线程，无论源搁在哪个架子上都以活跃未置顶起步）；**消息行归 chat**（`chatapp.Service.Fork` 走 `LoadThread` 取**耐久真相**［故 subagent 行与已折叠 block 一并带走，LLM 视图在装配时由分叉自己的水位 + `subagent_id` 过滤重新求得］→ 定前缀窗 → **预铸全部新 block id** 再逐条 `CreateMessage` 灌行）。预铸是必需的：`parent_block_id` 可能指向**更早**消息里的 block（subagent 回合挂在其父回合的 tool_call block 上），故整张 remap 表必须在任何行落地前就存在；`seq` 由 `insertBlocks` 按重放顺序连续发、自然从 1 重排，`context_role` 留空即取默认 hot，而 hot **就是**重置。**summary 两分支的要害**：摘要折叠了源里所有 `seq ≤ 水位` 的 block，携带它**只在**前缀真正**到达**那条线时才诚实；切在水位之前会让分叉继承一份描述它根本没有的回合的摘要——摘要就撒了谎、LLM 会就不存在的历史作答，故那一支 summary 与水位**都不带**（「尚未压缩」对一条短分叉正是事实）。携带时水位**必须重定基**（分叉把 block 从 1 重排，逐字带走源的数字会藏错行）：取被折叠 block 中**最大的新 seq**。摘要归属判定天然落在 chat——水位索引的正是它拥有的 block。**血缘边用已立法的 `create` 动词**（「conversation 创造实体（产生 v1）」正是实际发生的事：源线程产出了本线程的第一版），**不**新铸第 5 个边动词（4 动词集是 CHECK 强制的封闭词汇；两端 `from_kind`/`to_kind` 已说明 conversation → conversation，无需新词即无歧义），况且权威血缘本就在两列里；**刻意按分叉的入向侧 `SyncIncoming`**——diff-sync 会替换匹配（固定端, kindScope）的整个边集，而一个分叉永远只有一个父，故 replace-all 恰好精确、重复 fork 幂等；镜像地按**源**的出向侧写会是灾难：抹掉该对话曾建过的所有 function/handler/agent 的 `create` 边。搜索通知在行落地**之后**补发一次（头行的 `conversation.created` 发在线程还零消息时，否则投影会索引一个空对话）。**未复用 `CreateWithSystemPrompt`**：它只造 title+systemPrompt，分叉头还要 attachedDocuments/modelOverride/summary/水位/血缘五项，先 Create 再 Update+SetSummary 是三趟往返 + 一个仍缺的 setter，故 `Fork` 是同层一个新方法、共用同一 `emit`。

**Unarchive**：chat Send 的自动解档入口（给归档线程发消息即隐式唤回）。**MarkSeen**：`POST /{id}:seen` 动作清 `unread`——经 chat 的 `{idAction}` 派发器路由（与 `:cancel` 共一处理器，Go ServeMux 每模式一处理器），但纯属对话元数据故转发到 conversation 端口；幂等（未知/已删 id no-op 返 204）、**不发任何通知**（高频、单用户、对别的客户端无意义）。**Delete 连带停生成**：可选 `GenerationCanceler` 端口（chat 满足、后注入破环）——删对话先 cancel 在途生成，已删线程不再烧 LLM/推流。

## 2. 契约（引用）

LLM 工具：`search_conversations`（内容混合检索历史对话——只返 conversationId/title/snippet/messageId，绝不返全文；回忆是指针、不是上下文倾倒。**是内容回忆、非枚举**：只返消息匹配查询的线程、无匹配文本的漏掉，描述明禁当作完整列表，F146）· `list_conversations`（**忠实游标分页枚举**——答「列出我所有对话」的正路、补 search 的内容回忆缺口；复用 `Service.List`（ListFilter）、无新端点/表/码；返 id/title/archived/pinned/lastMessageAt 轻量行；默认仅 active、`includeArchived` 含归档；剩余页时返 `nextCursor` 使一页不被误当全集）· `manage_conversation`（归档/置顶/**改名本**对话——`action: archive|unarchive|pin|unpin|rename`（rename 需 `title`、复用 `UpdateInput.Title`），复用 `Service.Update` 的 PATCH 面、无新端点/表/码；从 ctx 取 conversationId，对话外降级 tool-result 串。描述声明**压缩是自动的**——无手动 compact/summarize 动作、无 UI 按钮，杜绝 agent 臆造按钮（含 rename 不臆造 UI 手势，F107）+ **给归档线程发消息会自动解档**（F106——使 agent 能警告，而非让下条消息静默撤销 archive 当前 thread）；chat system prompt 的 `conversation_management` 段同述此真相）。

端点（CRUD + `:seen` + `:fork` + `:retry` + **`GET /{id}/workdir`**［驻地投影，N4 有界投影之「零参数单对象」形］）→ [api.md](../api.md) · 表 `conversations` → [database.md](../database.md) · 码 `CONVERSATION_*` **4 个** → [error-codes.md](../error-codes.md)（**WD1 引入恰一条新码 `CONVERSATION_INVALID_WORK_DIR`**［422］——它守的是一个**物理**不可能：相对的根扎不住任何东西，以它解析出的路径仍是相对的、随后被 PathGuard 拒掉，于是线程带着一个**静默无效**的驻地；这不是校验剧场）（**`:fork` 不引入新码**：未知 `atMessageId` 复用 `MESSAGE_NOT_FOUND`［message id 是坐标，与 `?around=` 同一身份锚点 404］、未知对话复用 `CONVERSATION_NOT_FOUND`，其余情形无物理失败——空 body / 空 `atMessageId` 是合法的「从最新处分叉」、无消息的源是合法的纯配置副本、源在生成中也不冲突（fork 只读源、只往新对话追加）。为凑一条码而造校验剧场违反设计原则 #6）（含 `CONVERSATION_ATTACHED_DOC_NOT_FOUND`——PATCH `attachedDocuments` 引用不存在/已删 doc id 时 attach-time 即 422、Details 带缺失 id，照 agent knowledge 挂载的 eager 校验；F167 渲染时警告仍兜底此处不回溯的老数据，F168-M5；经 `SetDocumentResolver` 后注入启用、破 conversation↔document 环）· ID：`cv_`。被消费：chat（每回合读配置 + `:fork` 的消息半 + `:retry` 的版本指针——`:retry` 完全住在 chat／messages 侧，**不碰本表任何列**：换模型重试是逐回合的，绝不回写 `model_override`，见 [chat.md](chat.md) §3.5）、relation（conversation↔实体的 create/edit 边的另一端；**`:fork` 另发一条 conversation→conversation 的 `create` 边**——同一动词的唯一同类端对，见上 Fork）、touchpoint（对话触点台账——Delete 经 `SetTouchpointPurger` 级联硬删整份台账，与 relation purge 同款；台账见 [touchpoint.md](touchpoint.md)）、aispawn（`:iterate`/`:triage` 创建）。
