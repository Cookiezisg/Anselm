# 0015 — 视频进免费档:受管路由是唯一的两次请求形态,句柄签名、钱落提交

## 背景 / Context

[ADR 0013](0013-video-generation-synchronous-tool.md) 的「影响」节里有一句:

> **视频不进免费档**(P8,与本决策独立但同批):网关不开视频路由,`generate_video` 只在直连侧按 §3.5
> 注入。受管路由上,这个工具**诚实缺席**。

**那句话不成立,而且它的来历有问题**。它源自工单 §1 一张标题为「用户已拍板」的表里的 P8 一格,而 P1–P7
每一格都附着用户原话,**唯独 P8 那一格没有**——它是我自己的判断,被误记成了用户的决定,并据此驱动了真实
代码(网关无视频路由、`videoProviders` 无 `anselm` 条目、播种跳过 `ScenarioVideo`、设置里视频行无受管
选项、两处守卫测试把「受管无视频」钉死)。

用户读到后直接推翻:

> 「视频要进免费档的。我们要的是一个端到端的完整多模态」

并定下额度:**一人一天 10 条**。

ADR 不可变,故本篇**新立**,以更正 0013 影响节的那一句;0013 的**决策本身**(生成同步等完、不做后台
作业)不受影响,继续有效。

## 决策 / Decision

### 一、视频进免费档,与图像、语音**完全同形**

网关开两条路由(`POST /v1/videos/generations` + `GET /v1/videos/{videoId}`);桌面端 `videoProviders`
以 `anselm` 打头,与另两张表一样;`SeedDefaultsIfUnset` 播全部六个 scenario;设置里视频行有受管选项。

**为什么不留一个「视频除外」的特例**:一个只在其中一个模态上缺席的免费档,要求用户理解一条他没有理由
知道的规则。而「端到端的完整多模态」这句话的意思正是:**没有例外**。

### 二、视频是唯一的**两次请求**能力,故它的句柄必须**签名**

别的能力(chat / image / speech)都在一次 HTTP 请求里开始并结束,故「谁有权读这个结果」这个问题从来
不必问。视频先提交、桌面端几分钟后才轮询,而这两次请求之间那个答案必须由**某个东西**带着。

那个东西是句柄:`base64url(taskId).base64url(HMAC-SHA256(key, installId ‖ 0x00 ‖ body)[:16])`,常数时间
比较。install id 在 MAC **之内**却不在句柄之内——桌面端本来就知道自己是哪个 install,把它放上线缆只是
白白公开它。

**为什么不裸转发上游 task id**:那样任一 install 都能枚举并读走**别人**的视频 URL。

**为什么密钥不是一个新 env**:它由 `MEDIA_SIGNING_SECRET` **域分离**派生
(`HMAC(secret, "anselm-gateway-video-handle-v1")`),每次 config load 重算、不落任何地方。开视频因此不必
让运营者再放一个要轮换、要防泄的 secret,而其中一把被攻破仍伪造不出另一把。`VIDEO_ENABLED=true` 而
secret 缺席则**启动即失败**。

**签名验不过与上游已忘掉该任务同答 `VIDEO_TASK_NOT_FOUND`**:区分两者等于向调用方确认「它刚猜中的那个
句柄属于**别的** install」。

### 三、钱**落在提交**,轮询绝不动钱

一次在上游失败的生成**照样付费**。

**为什么**:另一条路是「只有客户端肯回来轮询时才退款」的路径,那意味着**走开的人白拿视频、等着的人
付钱**。免费档的钱绝不能取决于有没有人回来看。唯一会退的仍是可证明未计费的显式上游拒绝(GW-INV-50);
超时、5xx、200 却没有 task id 一律保留全额。

### 四、两个账本刻意数**不同的单位**

钱按**秒**报价(`InputVideoSeconds`);`install_category_daily` 的 `video` 品类按**条**配给(恒 1 units,
`VIDEO_DAILY_LIMIT` 默认 10)。

**为什么不都按秒**:按秒配给只会让用户写更短的提示词,而不是少生成视频。人心里配给的是**整条片子**。

## 影响 / Consequences

- **[ADR 0013](0013-video-generation-synchronous-tool.md) 影响节的「视频不进免费档」一句作废**。0013 的
  决策(同步等完、不做后台作业)不变——它在受管路由上同样成立:桌面端仍然同步等,只是等的对象从
  DashScope 换成了网关。
- **受管路由多了一次网络跳**,故轮询节奏仍取 wan 的 15s:网关只是转发,把网关轮询得更紧只会让网关把
  DashScope 轮询得更紧。
- **`generate_video` 的诚实缺席条件变窄了**:此前「只有受管 key」= 缺席,现在只有「一把能生成视频的 key
  都没有」才缺席。缺席本身仍是铁律——一个模型看得见却永远用不了的工具,会让它向用户许下一段交付不了的
  视频。
- **真钱验收已过**(2026-07-27):经生产网关真生成一条 720P/5s,轮询约 90s 到 `succeeded`,下载
  2,491,742 字节 `video/mp4`。探针 `backend/internal/infra/llm/live_managed_test.go`(`EVALS_MANAGED=1`
  门控,不入 `make verify`)。
- **记录教训**:一个没有原话依据的决定被记进了「用户已拍板」表,并驱动了五处真实代码与两处守卫测试。
  那张表此后**按证据分栏**——有原话的与我代拍的分开列,代拍的显式标记为代拍。

## 备选 / Alternatives

| 方案 | 为何未选 |
|---|---|
| 视频留在直连侧、免费档不供 | 用户明确推翻;而一个只在一个模态上缺席的免费档,要求用户理解一条他没有理由知道的规则 |
| 裸转发上游 task id 给客户端 | 任一 install 都能枚举并读走别人的视频 URL |
| 句柄写进一张新表、按行校验归属 | 要建表、要 GC、要迁移;签名是无状态的、跨重启有效、零 schema 改动 |
| 新增 `VIDEO_SIGNING_SECRET` env | 让运营者多一个要放、要轮换、要防泄的 secret;域分离派生同样安全且零部署摩擦 |
| 轮询到 `failed` 时退款 | 只有客户端肯回来时才跑的退款路径 = 走开的人白拿、等着的人付钱 |
| 品类账本也按秒配给 | 用户会写更短的提示词,而不是少生成视频;人配给的是整条片子 |
