# 0013 — 视频生成留在工具里同步等完,不建异步作业系统

## 背景 / Context

WRK-082 批D 要给桌面端加 `generate_video`。与出图、出语音不同,**每一家视频生成 API 都是异步任务制**
(提交拿 task id → 轮询 → 分钟级后取回产物),而不是一次请求拿结果。

这个形状差异诱人地指向一个更大的答案:项目**已经有**一台 durable 执行引擎(`flowrun_nodes` 行表 +
record-once 记忆化 + 解释器幂等重走),它天生就是为「长时间运行、要能崩溃恢复的东西」造的。把视频生成
挂上去看起来是复用地基。

同样诱人的是第二个形态:**提交后离场**——工具立刻返回「已提交」,视频在后台生成,完成时经 notifications
送达。这样一个回合不会被一段几分钟的等待占住。

本篇记录**两个都不做**,以及为什么。

## 决策 / Decision

**V1 形态**:`generate_video` 的 `Execute` 内部完成「提交 + 轮询 + 取回」,**同步等完**;等待期间经
`loop.ToolProgress` 把轮询状态作为 `progress` 块流给前端,工具卡渲进度。

三条与之配套的既有机制,一条新的都不加:
- **不加流**:progress 走既有 messages 流(E1 三条流永不再加)。
- **不加块型**:`progress` 是既有七型之一(E2 ephemeral delta + close 快照)。
- **不加超时轴**:回合墙钟 `timeout.chatTurnSec` 默认 1800s,足够覆盖各家的分钟级生成。

### 否决一:挂 durable flowrun 引擎

引擎的记忆化单位是**工作流节点**,而 `generate_video` 是**一次聊天回合里的一个工具调用**。要把它挂上去,
必须先让「聊天回合中途的一个工具」变成一个可记忆化、可重走的 flowrun 节点——那不是复用地基,那是把
**聊天**改造成工作流引擎的一个客户。代价包括:回合与 flowrun 的生命周期要对齐(用户关掉对话时那个 run
该怎么办?)、tool_result 要能在回合早已终结之后回填、`record-once` 的幂等键要为「同一回合同一工具的第
N 次调用」定义。这些都是真问题,而它们**全部由「同步等完」免掉**。

引擎该为工作流服务;一次聊天里的等待不是工作流。

### 否决二:提交后台 + 通知送达

这条更像产品判断而非架构判断:它把 chat 工具改造成了一套**异步作业系统**——需要作业表、需要「我的作业」
的查看面、需要作业失败的重试语义、需要一条从通知跳回原对话原 tool_call 的深链。而用户按下「生成一段
视频」时的心智是**我在等它**,不是**我提交了一份工单**。

更要紧的是它会**割裂产物与上下文**:视频在几分钟后到达时,那一轮对话早已结束,模型再也看不到它——不变量③
(消费咽喉)在那一刻断掉,而修复它又要把「回合结束后仍能给模型补喂内容」这件事发明出来。

### 什么会推翻这两条

**十分钟级的等待需求**。今天各家的文生视频在分钟量级,同步等待只是「一个略慢的工具」;当某个真实用例
需要等十分钟以上(长视频、批量),同步等完就会开始与「用户想在等待期间接着聊」冲突。**那时另立新 ADR**,
并且很可能会选否决二(离场形态)而不是否决一——因为届时真正缺的是「作业」这个产品概念,不是 durable 重走。

## 影响 / Consequences

- **一个回合被一段视频生成占住**。这是接受的代价:同一对话的下一条消息在生成期间被 409 `STREAM_IN_PROGRESS`
  拒(既有队列语义,非新增)。用户可以开另一个对话。
- **视频不进免费档**(P8,与本决策独立但同批):网关不开视频路由,`generate_video` 只在直连侧按 §3.5 注入。
  受管路由上,这个工具**诚实缺席**。
- **崩溃即丢**:进程在轮询中途死掉,那次生成的钱已花而产物拿不到(上游仍会完成,但我们不再持有 task id)。
  这正是 durable 引擎能解决的那个问题——它被**明知地**换成了不引入上述全部代价。等待期是分钟级、桌面端是
  单用户单进程,这笔交换在 V1 成立;它不成立的那天,就是重开 ADR 的那天。
- **产物渲染**:V1 落 mp4 附件、渲文件卡(可在外部打开)。**内联播放另作决定**——它要引入桌面视频播放栈
  (`media_kit`/`video_player` 的原生依赖),那是一次独立的依赖决策,不该搭在本批里。

## 备选 / Alternatives

| 方案 | 为何未选 |
|---|---|
| durable flowrun 节点 | 引擎为工作流而生;把聊天回合里的一个工具变成可记忆化节点,需要发明回合↔run 生命周期对齐、回合终结后回填 tool_result、逐调用幂等键——三个真问题,全部由同步等完免掉 |
| 提交后台 + 通知送达 | 把 chat 工具改造成异步作业系统(作业表/查看面/重试语义/深链);且**割裂产物与上下文**——视频到达时那轮对话已结束,模型再也看不到它,不变量③当场断掉 |
| 独立的「生成任务」实体(第五个 Quadrinity 成员) | 违反设计原则 #1 的封闭集;而且它要解决的问题(等待可见、可恢复)在分钟量级上由 progress 块 + 回合墙钟已经解决 |
