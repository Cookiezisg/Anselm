# EDGE-030 · 生成中再 Send · 真实 App 五通道复验

## 判定边界

本次复验区分两条产品入口，避免把 HTTP 并发合同与 Composer 的输入体验混为一谈：

- 直接对正在生成的 conversation POST 新消息，服务端必须立即返回 `409 STREAM_IN_PROGRESS`，不得创建第二个 assistant turn。
- 用户在真实 Composer 中继续输入并按 Enter，是当前前端 Chat 契约规定的“生成中排队发送”：消息进入可见 FIFO 队列，不与当前 turn 并发；当前 turn 收尾后再按序发送。

原始清册此前把两条入口压成“409，不排队”，与已经落地并有产品文档说明的 Composer queue 实现发生漂移。本次同步原始提取物只澄清入口语义，没有放松五级验收、五通道要求或顺序门。

## 真实结果

1. 真实 App 创建新 conversation，并发送长响应请求；backend journal 记录 `POST /messages = 202`。
2. 首轮仍处于生成态时，Composer 通过真实键盘输入第二条消息并按 Enter；画面显示 `1 waiting to send` 和消息 chip，同时保留 `Stop generating`。没有第二个 assistant turn 被并发启动。
3. 同一生成窗口内，独立直接 POST `direct concurrent probe` 得到：

   ```text
   HTTP/1.1 409 Conflict
   {"error":{"code":"STREAM_IN_PROGRESS","message":"this conversation already has an assistant turn running","details":null}}
   ```

4. backend journal 对应记录为 `POST /api/v1/conversations/cv_ad02a321bf035050/messages = 409`；该请求没有对应 LLM tap 请求，也没有新的 durable user/assistant 回合。
5. ssetap 记录首轮 messages 流连续 delta，未观察到由并发 POST 产生的第二个流；entities/notifications 三流均已连接并落盘。
6. llmtap 记录真实受管网关 completion 请求；前端日志没有 Flutter/Dart/布局异常。日志中的 macOS IMK mach-port diagnostic 已原样保留，未被静默过滤；它不包含 `FlutterError`、`DartError`、`Unhandled exception` 或 `RenderFlex`。

## 账本边界

- L1 既有 focused/race 证据已覆盖服务端 409 合同；本 session 补充真实 App 中“继续输入不丢失”的用户目的证据。
- L2 本 session 具备 manifest、backend journal、sse journal、frontend journal、llm journal 和真实窗口录像，可用于五通道复核。
- L3 仍需带动作时间戳的独立 `measure latency` 证据，不以 Computer Use 调用返回时间替代用户感知时延。
- L4 仍需对 queue chip 的几何、圆角、字重、对比度做本格独立测量；本文件的截图只作为定位证据。
- L5 仍需从干净用户状态重新验证 Composer queue 的可发现性；本次使用了已知操作，不冒充从零发现。
